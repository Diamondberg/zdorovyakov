# ЧАСТЬ I. КОНЦЕПЦИЯ

## 1. Назначение системы

Создать центральную торговую платформу «ЗДОРОВЯКОВ».

Платформа включает:

- Основной сайт бренда.
- Единую базу данных.
- Центральный backend.
- Административную панель.
- Управление товарами.
- Управление покупателями.
- Управление заказами.
- Корзину.
- Акции и скидки.
- Доставку.
- Email-уведомления.
- Аналитику.
- API подключаемых лендингов.

Первый подключаемый лендинг — **водный-прополис.рф**.

В будущем можно подключать неограниченное число других тематических витрин.

## 2. Архитектурный принцип

**ОДНО ЯДРО — ОДНА БАЗА — МНОГО ВИТРИН.**

Пример:

ЗДОРОВЯКОВ
- Центральный сайт.
- Backend/API.
- База данных.
- Админка.
- Витрина №1: водный-прополис.рф.
- Витрина №2: будущий продукт.
- Витрина №N: будущий продукт.

Каждая витрина получает уникальный `storefront_id`.

Каждый заказ сохраняет свой источник.

У лендингов нет отдельных баз клиентов и заказов.

Основной сайт не должен технически зависеть от доступности отдельного лендинга.

## 3. Цель MVP

Запустить работающую инфраструктуру продаж одного продукта.

Бизнес-ориентир — **1000 постоянных покупателей**, а не просто 1000 контактов или заявок.

Нужно измерять количество уникальных покупателей с подтверждёнными покупками и долю повторных заказов.

# ЧАСТЬ II. ПРОДУКТ И КОММЕРЧЕСКАЯ МОДЕЛЬ

## 4. Первый товар

**Вода прополисная «ЖИВА» 30%, 100 мл.**

Исходные данные:

- Розничная цена: 470 ₽.
- Закупочная цена: 275 ₽.

Параметры хранятся в центральном каталоге.

Закупочная цена является внутренней коммерческой информацией и не передаётся публичному API.

Характеристики, состав, фото, документы и описание использовать из достоверных материалов производителя.

Не генерировать вымышленные сертификаты, отзывы, медицинские свойства или факты о производителе.

## 5. Сценарии покупки

На первом лендинге обязательно четыре видимых варианта:

| Количество | Название | Смысл |
|---|---|---|
| 1 флакон | **На пробу** | Первое знакомство |
| 3 флакона | **Мне на месяц** | Личный месячный комплект |
| 6 флаконов | **Нас двое** | Месячный комплект для двоих |
| 9 флаконов | **Мы семья** | Месячный семейный комплект |

**Важно:** 3, 6 и 9 флаконов представлены как варианты месячной покупки, а не как запас на несколько месяцев.

При этом названия комплектов отражают коммерческие сценарии выбора, а не обязательную медицинскую норму потребления для каждого человека.

В интерфейсе должны быть понятны:
- Название комплекта.
- Количество флаконов.
- Цена.
- Действующая акционная скидка.
- Итоговая экономия.

Предусмотреть возможность выбора произвольного количества от одного флакона.

## 6. ВРЕМЕННАЯ СТАРТОВАЯ АКЦИЯ

На этапе запуска применяется акция в честь открытия «ЗДОРОВЯКОВ».

**Скидки временные, а не постоянные.**

Условия:

| Количество | Скидка | Итог |
|---|---:|---:|
| 1–5 флаконов | 0% | 470 ₽/шт. |
| 6–8 флаконов | 10% | 423 ₽/шт. |
| 9 и более | 15% | 399,50 ₽/шт. |

Примеры:

- 1 флакон — 470 ₽.
- 3 флакона — 1410 ₽.
- 6 флаконов — 2538 ₽.
- 9 флаконов — 3595,50 ₽.

Позиционирование:

**«Стартовая акция в честь открытия!»**

Для шести флаконов можно использовать формулировку «Скидка для двоих», для девяти — «Семейная скидка», но исключительно в рамках действующей акции.

Запрещены формулировки:
- «Постоянная скидка».
- «Навсегда».
- «Пожизненная скидка».
- «Всегда минус 15%».

### Управление акцией

В админке должны настраиваться:

- Название.
- Начало.
- Окончание.
- Применимые товары.
- Пороги количества.
- Процент скидки.
- Активность.
- Возможность досрочного прекращения.

Дата окончания акции должна быть реальной, а не искусственным таймером.

Исторические заказы сохраняют первоначальные цены и скидки.

При завершении акции обычные цены восстанавливаются автоматически.

Не показывать клиентам несуществующие скидки.

## 7. Будущая бонусная программа

**В MVP НЕ РЕАЛИЗОВЫВАТЬ.**

После появления достоверного учёта оплаченных покупок планируется переход к начислению бонусных баллов для последующих заказов.

В перспективе:
- Начисление баллов за покупки.
- Использование баллов на следующие покупки.
- Реферальная программа.
- Вознаграждение за подтверждённые покупки приглашённых.

Предварительная реферальная идея — 15% в бонусах.

Это будущая функция, не действующая акция.

Не смешивать обещание будущих бонусов с текущими скидками.

Не разрабатывать реферальный кабинет и бонусные балансы сейчас.

Для будущего расширения предусмотреть возможность добавления соответствующих сущностей без разрушения текущей структуры БД.

# ЧАСТЬ IV. ОФОРМЛЕНИЕ ЗАКАЗА

## 10. Правильный пользовательский сценарий

**Выбор комплекта → Корзина → Данные получателя → Предварительный расчёт доставки → Проверка email → Отправка заказа → Центральная БД → Админка → Обработка заказа.**

Нет отдельной регистрации.

Нет личного кабинета.

Нет оплаты через сайт.

## 11. Корзина

Корзина должна поддерживать несколько товаров.

В MVP в ней один вид товара.

Показывать:
- Наименование.
- Количество.
- Стоимость единицы.
- Акционную скидку.
- Экономию.
- Общую стоимость товаров.
- Доставку отдельно.
- Итоговую стоимость, когда она определена.

Изменение количества автоматически пересчитывает сумму.

Все денежные расчёты подтверждаются центральным backend.

## 12. Данные получателя

Поля:
- Имя.
- Фамилия.
- Телефон.
- Email.
- Страна/регион.
- Город.
- Почтовый индекс при необходимости.
- Адрес доставки или пункт получения.
- Комментарий.

Перечень обязательных полей зависит от способа доставки.

Отдельное согласие на рекламные сообщения не должно быть обязательным для оформления заказа.

## 13. Валидация email

Обязательная проверка владения адресом при первом заказе.

Последовательность:
1. Ввод email.
2. Проверка синтаксиса.
3. Проверка почтового домена.
4. Отправка шестизначного кода.
5. Ввод кода.
6. Подтверждение адреса.

Код действует 10 минут.

Необходимы:
- Защита от перебора.
- Ограничение количества отправок.
- Повторная отправка.
- Сохранение формы при проверке.
- Обработка ошибок почтового сервиса.

Повторное оформление на подтверждённый адрес можно упростить с помощью безопасной проверки владения им, без создания пароля.

Нельзя предоставлять историю заказов только на основании введённого email.

## 14. Валидация телефона

- Поддержка российских номеров.
- Приведение к формату +7.
- Проверка длины.
- Удобное исправление.
- Телефон без SMS-подтверждения считается неподтверждённым.

Не объединять покупателей исключительно по неподтверждённому телефону.

## 15. Предварительный расчёт доставки

Предусмотреть возможность будущего подключения API транспортных компаний.

На старте использовать:
- Доступные тарифы.
- Расчёт по адресу и параметрам отправления, если возможен.
- Либо уведомление «Стоимость доставки уточняется».

В системе должны быть сведения о весе и габаритах товаров и упаковки.

Без достоверного тарифа не показывать выдуманную стоимость доставки.

## 16. Создание заказа

После отправки формы:

- Создать уникальный номер заказа.
- Создать или идентифицировать клиента.
- Сохранить состав корзины.
- Сохранить цены и скидки на момент оформления.
- Сохранить данные доставки.
- Сохранить источник витрины.
- Записать заказ в центральную БД.
- Передать событие в систему уведомлений.
- Показать покупателю подтверждение.

Не создавать дубли при повторном нажатии кнопки.

Отправленная заявка не считается оплаченной.

У «ЗДОРОВЯКОВ» одна центральная админка.

Отдельная CRM не требуется.

Все лендинги передают данные в единую систему.

## 18. Клиенты

Каждый клиент имеет внутренний `customer_id`.

Карточка:
- Имя и фамилия.
- Email.
- Статус подтверждения email.
- Телефон.

Администратор может искать, фильтровать и редактировать клиентов.

## 19. Редактирование карточки клиента

Разрешить корректировать:
- Имя.
- Фамилию.
- Телефон.
- Email.
- Адрес.
- Индекс.
- Город.
- Комментарии.

Все изменения фиксируются.

Изменение email требует подтверждения нового адреса.

Проверять возможные дубликаты.

Не объединять разные карточки автоматически при случайном совпадении данных.

Не изменять задним числом данные уже отправленных посылок.

## 20. Заказы

В админке показывать:
- Номер.
- Дату.
- Клиента.
- Источник.
- Состав.
- Количество.
- Стоимость.
- Скидку.
- Доставку.
- Оплату.
- Сборку.
- Отправку.
- Трек-номер.
- Комментарии.

### Статус обработки

- Новый.
- Подтверждён.
- Собирается.
- Собран.
- Отменён.

### Статус оплаты

- Не оплачен.
- Оплачен.
- Возврат в обработке.
- Возврат выполнен.

### Статус доставки

- Не отправлен.
- Подготовлен.
- Отправлен.
- В пути.
- В пункте выдачи.
- Доставлен.
- Возвращён.

Статусы обработки, оплаты и доставки должны храниться отдельно.

### Дополнительные действия

- Внести или исправить трек-номер.
- Назначить перевозчика.
- Исправить данные заказа.
- Изменить статус.
- Добавить комментарий.
- Отправить письмо клиенту.
- Запросить уточнение данных.
- Отменить заказ.
- Зафиксировать возврат.

Каждое действие сохраняется в журнале.

## 21. Запрос уточнения данных

В админке предусмотреть кнопку:

**«Запросить уточнение данных»**

Сценарий:

1. Администратор выбирает заказ.
2. Указывает, какие данные требуется уточнить.
3. Система отправляет письмо на подтверждённый email.
4. Покупатель открывает защищённую ссылку.
5. Исправляет данные.
6. Система обновляет разрешённые поля заказа.
7. Администратор видит изменение.

Ссылка одноразовая, с ограниченным сроком действия.

# ЧАСТЬ VI. УВЕДОМЛЕНИЯ

## 22. Центральная система email

При изменении статусов отправлять автоматические сервисные письма.

| Событие | Уведомление |
|---|---|
| Заказ создан | Заказ №... принят |
| Подтверждён | Заказ подтверждён |
| Оплачен | Оплата получена |
| Собирается | Заказ комплектуется |
| Собран | Заказ готов к отправке |
| Отправлен | Отправлен, перевозчик и трек-номер |
| В пути | Заказ находится в пути |
| В пункте выдачи | Можно забрать |
| Доставлен | Заказ доставлен |
| Отменён | Уведомление об отмене |

Система не должна отправлять уведомление «В пути» без соответствующего фактического статуса.

Уведомления отправляются на подтверждённый email.

## 23. Технические требования к email

- Единый почтовый модуль.
- Фирменные шаблоны.
- Очередь уведомлений.
- Повторные попытки при ошибке.
- Журнал отправки.
- Защита от дублирования.
- Возможность повторной отправки администратором.
- Поддержка настройки SPF/DKIM/DMARC.
- Раздельные сервисные и рекламные коммуникации.

Не считать письмо прочитанным только потому, что почтовый сервер его принял.

# ЧАСТЬ VII. АНАЛИТИКА

## 24. Показатели

- Созданные заказы.
- Оплаченные заказы.
- Доставленные заказы.
- Уникальных покупателей.
- Повторные покупки.
- Количество проданных флаконов.
- Средний чек.
- Применённые скидки.
- Выручку.
- Расчётную валовую прибыль.
- Источники привлечения.

## 28. Режим автономной разработки

Владелец проекта может отсутствовать продолжительное время.

Разработчик должен максимально самостоятельно выполнять безопасные действия в пределах уже предоставленных полномочий.

Разрешается:
- Анализировать существующий код.
- Создавать проектные файлы.
- Писать и редактировать код.
- Запускать локальные тесты.
- Исправлять ошибки.
- Создавать документацию.
- Работать с Git в отдельной ветке.
- Выполнять безопасные локальные проверки.

Не выполнять без необходимого разрешения:
- Удаление рабочих данных.
- Разрушительные миграции.
- Отключение безопасности.
- Изменение системных прав.
- Изменение DNS.
- Production-развёртывание.
- Реальную рассылку покупателям.
- Подключение платных сервисов.

Не пытаться обходить обязательные разрешения среды выполнения.

Если действие заблокировано, документировать проблему и продолжать другие доступные задачи.
