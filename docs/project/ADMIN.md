# Административная панель — этап 3

Локальный адрес `/admin/`, API `/api/v1/admin`. Публичного deployment нет.
Перед реализацией владелец просмотрел нарисованный макет и дал конкретные правки;
они включены в интерфейс. Снимки локального QA: docs/reports/images/.

## Запуск

1. `npm ci`, `npm run build`.
2. `npm run db:local` в отдельном терминале.
3. `npm run db:migrate` (три миграции, включая 003_admin.sql).
4. В игнорируемом `.env` задать ADMIN_EMAIL и ADMIN_BOOTSTRAP_PASSWORD
   (14–256 символов), ADMIN_ORIGIN=http://127.0.0.1:3000,
   ADMIN_INSECURE_LOCAL_COOKIE=true только для local HTTP.
5. `npm run admin:create` создаёт первого local owner. Без паролей по умолчанию,
   не заменяет существующих пользователей. Удалить bootstrap-пароль из .env после использования.
6. `npm run dev`, открыть http://127.0.0.1:3000/admin/.

Для самостоятельного тестирования с синтетическими данными: `npm run admin:preview`.
Открыть http://127.0.0.1:5187/admin/. Случайные credentials — tmp/preview-login.json,
не печатаются в журнал и не коммитятся. БД отдельная, только loopback.
Preview — не рабочий магазин, не production и не место реальных персональных данных.

## Доступ

- Пароли: асинхронный scrypt N=32768,r=8,p=3, соль 16 random bytes, ключ 64 bytes;
  сравнение timingSafeEqual. Пароль и hash не возвращаются API.
- Сессия 8 часов: 32 случайных байта, в БД только SHA256, отзыв при выходе;
  активность администратора и текущая роль проверяются на каждом запросе.
- Production: __Host cookie, HttpOnly, Secure, SameSite=Strict, Path=/, без Domain.
  Небезопасная cookie разрешается исключительно явным local dev flag;
  в NODE_ENV=production Secure принудителен и ADMIN_ORIGIN обязан быть HTTPS.
- Для POST/PATCH/PUT нужен точный Origin и X-CSRF-Token. CSRF выводится из
  высокоэнтропийной cookie, возвращается login/me; cookie недоступна JavaScript.
  GET не отдаёт CORS-доступ чужому origin.
- Лимиты входа общие в PostgreSQL: 20 попыток/IP, 10/email за 15-минутное окно,
  считаются и неуспешные входы. IP/email хешированы в buckets; ответы не раскрывают
  существование пользователя. Очистку истёкших buckets добавить в эксплуатационный worker.
- owner: все разделы, цены, акции, аудит и подтверждение платежей/возвратов.
- manager: клиенты, заказы, обработка/доставка, комментарии; не цены, не изменение
  акций и не подтверждение оплаты. Закупочная цена скрыта от manager.
- HTTP не содержит публичной регистрации администраторов и покупательского checkout.

## Разделы и правила

Сводка: новые заказы с полуночи Asia/Tomsk; ожидающие оплаты и готовые к отправке —
текущая очередь; получено сегодня — подтверждённые платежи минус подтверждённые
возвраты, по confirmed_at. Это ручной учёт фактических операций, не банковская интеграция.
Неоплаченные заявки не увеличивают выручку. Показатели не демонстрационные в UI:
они приходят из БД; только QA preview содержит явно синтетические данные.

Заказы: поиск по номеру/имени/email/телефону, три фильтра статусов, pagination 25.
На узком экране карточки вместо таблицы; нет одновременного empty-state и таблицы.
Детали — модальная выдвижная панель с native focus trap и Escape/закрытием.

Обработка, оплата и доставка независимы. Сервер проверяет допустимые переходы.
История сохраняет actor_id, timestamp, предыдущий и новый статус. Все записи
изменяются с optimistic version: устаревшее сохранение даёт 409.

Ручная оплата и возврат: отдельная форма владельца, явное подтверждение, точная
сумма и журнал. До оплаты необходимо уточнить стоимость доставки (0 допустим
только как реальное подтверждённое значение). После оплаты тариф не меняется.
Отправка требует собранного заказа, перевозчика и трека. Отмена отправленного
заказа запрещена; использовать возврат. Изменение адреса отправленной посылки запрещено.

Клиенты: контактные данные, адресная книга, комментарий, история заказов,
подтверждённые суммы и выполненные заказы. Новый email сохраняется как pending;
прежний подтверждённый email действует до проверки нового. Конфликт подтверждённого
email даёт 409, совпадение телефона — предупреждение, без автоматического объединения.
Изменение карточки клиента не меняет снимки заказов/посылок. Отправка кода для
pending email будет реализована на этапе 5; интерфейс честно сообщает это.

Товары: owner меняет розничную и закупочную цены; сохранённые заказы не пересчитываются.
Акции: owner задаёт товары, даты, пороги и активность; отключение снимает скидку
со следующих расчётов. Конфликты дат и конкурентное сохранение защищены lock/version.
Аудит записывает исполнителя и поля/версии изменений, цены и переходы статусов;
контакты/адреса, пароли, session tokens и комментарии не копируются в audit JSON.
Комментарии хранятся отдельно в закрытой таблице с автором и временем.

## HTTP API

| Метод | Относительный путь | Доступ |
|---|---|---|
| POST | /auth/login | Точный Origin, пароль, DB rate limit |
| GET | /auth/me | Сессия, actor и CSRF |
| POST | /auth/logout | Сессия + CSRF + Origin |
| GET | /summary | owner/manager |
| GET | /orders, /orders/:id | Поиск/фильтры/детали |
| PATCH | /orders/:id | version, получатель/адрес/доставка/перевозчик/трек |
| POST | /orders/:id/status | version, kind, value; оплата owner+confirm+amountMinor |
| POST | /orders/:id/comments | body, author из сессии |
| GET/PATCH | /customers/:id | Карточка и version-edits |
| GET | /customers | Поиск, offset |
| GET | /products | Закупочная цена только owner |
| PATCH | /products/:id/price | owner, version, retailPriceMinor, purchasePriceMinor |
| GET/POST | /promotions | Чтение / создание owner |
| PUT | /promotions/:id | owner, version, полный набор условий |
| GET | /audit | owner, offset |

Ошибки возвращают только код, без SQL/stack/ПДн. Статика ограничена dist/admin,
CSP запрещает чужие скрипты/фреймы, HTML noindex. Deploy, HTTPS и production-роли
по-прежнему отдельные согласованные действия этапа 8.
